# SpecDD 工作流

本目录是项目需求和开发进度入口。现状见 [项目基线](BASELINE.md)，进行中工作见 [需求总览](INDEX.md)，所有会话遵循 [开发守则](../AGENTS.md)。

## 状态与流转

沿用用户指定拼写 `planed`、`developing`、`implement`、`discard`，不得自行改成 planned/implemented。

| 目录 | 含义 | 流转条件 |
| --- | --- | --- |
| planed | 已记录、待澄清或待实施 | 明确目标、范围、初步方案和验收标准，获任务授权后开始实施 |
| developing | 实施中、阻塞、待验证或待验收 | 工作和必要检查完成；有用户验收要求时必须等到实际确认 |
| implement | 已实现且完成适用验收 | 保留实现、测试、交付证据；新扩展另建关联需求 |
| discard | 取消或被替代 | 写明原因、已做工作影响及替代需求编号 |

常规路径 `planed → developing → implement`；planed/developing 可进入 discard。implement 若发现原需求未完成可退回 developing；discard 恢复时回到 planed。每次移动更新 INDEX.md 和文档中的变更记录；Git 保存历史，不复制多份。

## 编号与文档

需求目录如 `SPEC-001-简短英文主题`（前缀来自 config.json），编号全仓唯一、递增、永不复用。创建前检查四个状态目录和 INDEX.md；多会话同时工作时避免认领相同编号，不覆盖已有修改。

标准需求包含 spec.md、tasks.md、verification.md，分别使用 templates/ 下的模板。小任务可合并为一份 spec.md，但必须保留需求、实施、测试用例、回归结果和交付信息。截图或小型必要附件可放需求目录；运行日志、大产物放被忽略的 tmp/ 或 data/，文档保留可读结论，不能只链接本机临时日志。

目录位置是状态唯一依据；文档只记录当前阶段（例如待用户验收）、更新时间、阻塞和下一步。INDEX 是脚本生成的导航摘要，不是第二套独立状态表；不要手改生成文件。通过 `python3 tools/specdd.py index` 同步。

## 实施闭环

1. 阅读相关 Spec 和代码，定义问题、范围/非目标、依赖与验收条目（AC）。
2. 开始执行时移动到 developing，拆解任务；涉及结构或跨服务流程时补充 Mermaid 流程图。
3. 实现与 Spec 同步；新增功能必须编写测试用例（TC），关联对应 AC。缺陷修复记录复现及修复后结果。
4. 根据影响选择增量或全量回归；记录理由、环境、测试范围和实际结果。
5. 检查失败/跳过/未执行项，保留原因与风险；必要验证未完成不能进入 implement。
6. 若范围含部署，记录部署版本与上线检查；若要求用户验收，保留 developing 等待结果。全部满足后移动到 implement，更新总览与相关文档。

## 回归范围

- 增量：仅影响单一明确模块，执行新用例、该模块现有用例及直接关联链路。
- 全量：公共能力、接口契约、权限、数据库/索引结构、依赖、核心链路、测试基础设施变化或影响无法确定。执行 PROJECT.md 中已配置的全量检查命令，按影响补充专项评估、端到端、设备或人工验证。
- 必须记录为何选择该范围。自动化用例本身可作为详细 case，验证记录需列明关联路径、前置条件、预期和实际结果。
- 真实付费服务和运行站点的写入验证单独判断授权与隔离条件；未执行就明确写明，不能把模拟通过写成真实外部验收。

## 历史与新需求

采用 SpecDD 前的功能在 BASELINE.md 按模块记录，不追溯伪造 Spec。docs/ 下的早期计划是历史材料，不得据其复活已取消事项或覆盖后续决定。新需求从本规范生效后完整流转。
