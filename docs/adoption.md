# 新项目与已有项目采用指南

## 新项目

1. 复制仓库内容，排除 `.git`、临时文件和缓存，保留四状态目录；不要复制原项目历史需求。
2. 填写 PROJECT.md，确定技术栈、代码目录、模块边界、数据规则和实际检查入口。
3. 首个需求创建前设置 spec/config.json 的 prefix（2–16 位大写字母/数字，以字母开头）；默认 SPEC。
4. 按实际情况填写 BASELINE.md；纯新项目明确“暂无业务实现”。
5. 运行模板自测与 check，创建需求，完善并展示 Spec，收到用户明确确认后记录，再开始实施。
6. 将模板工具测试、check 和业务测试整合到你的 CI/全量入口；本模板不预设某个 CI 平台。

## 已有项目

- 检查工作区和已有规范，先阅读现有 AGENTS.md；将公共规则合并进去，保留原有业务约束与子目录规则。
- 逐项迁入 spec/、tools/specdd.py、tests/specdd/ 和说明文档，检查命名冲突；不要覆盖原 README、PROJECT、测试或同名规范。
- 现有业务测试保留原运行时，再按功能/主题逐步拆分，确保独立运行及新目录被发现。
- 对实际现状建立基线；早期规划保留历史属性，不将未实现计划自动当成当前已授权待办。
- 原项目已有需求编号时明确迁移映射；不能把不同历史需求分配为同一编号，也不静默修改旧引用。
- 迁入动作本身关联本项目 Spec，编写 test case，并按影响决定增量/全量回归。

## 给后续会话的启动说明

可直接提出：“请先阅读 AGENTS.md、PROJECT.md、spec/README.md 和 spec/INDEX.md，再按 SpecDD 规范处理这个需求。”每个新需求先展示 Spec 等待明确确认，记录后才实施；确认后在约定范围内连续推进，不逐任务重复询问。

每次结束前同步任务、决定、验证与下一步。跨会话信息保存在仓库文档，不能只留在聊天记录。

## 模板升级

将模板仓库的公共规则与工具变更按差异合并，保留采用项目的业务规则、实际命令和历史 Spec。不要再次全目录覆盖已有项目；升级工具和测试基础设施后执行全量适用回归。

## 已有历史需求升级确认门槛

不要补造历史用户确认。确为采用本规则之前已实现的需求，审查历史后可将编号显式列入 spec/config.json 的 legacy_spec_ids，并在基线中记录理由。仅 implement 中的这些编号免除追溯确认；它们仍须满足原有完成验证门槛。新需求、planed、developing、历史需求重开均无此豁免。

历史在开发中的需求需要先向用户展示当前方案、取得真实确认，再继续实施。不要批量自动 confirm，不把采用规范的授权当作所有业务 Spec 的确认。
