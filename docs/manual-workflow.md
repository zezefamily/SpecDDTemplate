# 没有 Python / 管理工具时的 SpecDD 流程

适用于 Python 缺失、当前平台无法运行 CLI 等真实工具不可用情况。开发约束来自 [DEVELOPMENT.md](../DEVELOPMENT.md)，工具可用时优先使用现有 CLI。本路径不能绕过确认缺失/过期、失败测试或成果验收。

## 计划与确认

1. 阅读项目配置、INDEX 与四状态目录，选择未使用的稳定编号；先检查 Git 历史和其他会话，避免复用/冲突。
2. 复制 spec/templates 中的文档到 planed 下的新需求目录，填入目标、范围、方案、AC、任务与测试计划，并同步总览。
3. 展示具体 Spec，等待用户明确确认。原始需求、沉默、超时或 Agent 自行声明不算确认；此前只做调查和文档。
4. 确认后将已展示的 Spec 保留为不可改写的 approval-snapshot.md 证据快照，在 confirmation.md 记录需求编号、方案版本、确认人、确认日期/时间、用户原话与消息依据。这个快照是历史证据，不是第二份活跃需求，不单独流转。
5. 不伪造 CLI 的 proposal_sha256 或“已运行 confirm”。手工记录明确写“手工流程：工具不可用”，同时在 Spec 中标注实际确认依据。

## 实施与交付

用户已确认后移动需求目录到 developing，同步 INDEX 和变更记录。维护任务、关键决定与下一步；实质方案变化时先暂停相关实施，展示差异并重新确认，保留历次快照和依据。执行期勾选、日期、日志与实质方案分别核对。

新功能必须编写/更新 test case，缺陷修复补复现用例；按影响选择增量/全量回归并记录真实结果。必要验证未完成保持 developing。开发前确认不能代替开发后成果验收；需求要求用户验收时等待实际反馈。

全部满足后归档到 implement，取消时移到 discard，保留理由和替代编号。每次维护总览和历史，检查只有一份活跃需求，不能删除历史来重新分配编号。

## 恢复工具

- 先核对当前约定与用户确认快照，检查是否发生未确认的实质变化；有变化则先重新展示确认，不直接补录旧批准。
- 没有变化时，可以依据真实历史反馈运行 confirm 补录，source 明确注明“手工确认记录补录”，保留原始 confirmation.md/快照及原确认日期。工具时间是此次记录时间，不能冒充过去的执行时间。
- 重建 index 后执行 check，运行适用回归；记录工具发现的问题，不能为了过检查篡改原话或勾选未完成项。
- 历史已完成需求依据迁入规则显式审查，不自动批量生成批准记录，也不因工具恢复补造过去的测试。

这套手工证据与 CLI 记录没有伪装成同一种格式。工具检查开发中的需求时仍需要真实可核对的补录；业务测试命令是否可用另行说明，不把缺少 Python 当作所有测试都可跳过。
